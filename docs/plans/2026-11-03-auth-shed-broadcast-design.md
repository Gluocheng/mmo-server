# 登录过载与广播回包 策划文档

> **Status:** approved  
> **实施计划：** （策划通过后创建）[`2026-11-03-auth-shed-broadcast.md`](2026-11-03-auth-shed-broadcast.md)

**For agentic workers:** 签发和刷新拆开。密码哈希排队满了立刻拒绝。移动和聊天先给出请求结果，再异步广播。不改 cherry，不降低 bcrypt 成本。`Status: approved` 前不得创建实施计划、不得改业务代码。

---

## 背景与目标

2026-11-03 的最大人数复测里，2000 人同时签发有 474 个 `40005`。两个登录节点各 8 个 session 工人，密码哈希和刷新挤在同一组 Actor 里。成功请求的中位耗时已经到 10.9 秒，排过 `cluster.nats.request_timeout`（20 秒）的被网关记成登录服调用失败。当时登录进程大约用了 7 个核，机器还有空核。

同一批移动、施法、解禁后发言里，多数请求几百毫秒内返回，少数卡满客户端 20 秒没有响应。移动和聊天都是先把周围的人推完，再 `Response`。一个人的推送堵住，这个人的请求就一直占着 Actor。

**一期目标：** 刷新、登出、用 token 登录不排在新号哈希后面。签发排不下时马上返回「登录繁忙」，不再变成 `40005`。移动先改坐标并回包，聊天先判断能不能进广播队列再回包，推送都不挡请求。

---

## 用户场景

1. 2000 个新号同时签发。排得下的拿到 token。排不下的马上得到 `40036`，网关连接不被挂到 20 秒。
2. 上面这波签发还在算密码时，另一批已经在线的人刷新 token，仍然走 session 工人，不跟着哈希排队。
3. 一条主城线 200 人同时移动。每个人的 `game.player.move` 在坐标写入后就返回。周围的人随后收到 `onMove`，中间被挤掉的旧坐标可以不发，最后一档坐标要发到。
4. 一条主城线 200 人同时发言。广播队列有空位就回成功，再推 `onChat`。队列满了回 `40037`，不假装已经发出去。

## 功能范围

### 包含

- 每个登录进程两组子 Actor
  - `{node}.session.{n}`：`refreshToken`、`logout`、`authToken`，以及这两条路径上的封禁、维护检查。不计算密码哈希。个数仍是 `auth.session_workers`，默认 8
  - `{node}.pwd.{n}`：只处理 `issueToken`。个数为 `max(2, 核数/启用的登录节点数)`，并且不超过 `max_open_conns - session_workers - 4`。12 核、2 个登录节点、连接池 20、session 工人 8 时，每个进程 6 个
- 网关按方法选目标。签发轮询密码工人，其余轮询 session 工人
- 每个密码工人排队上限 32。人已经在队里的继续算完。新的签发如果该工人已满，不入队，直接 `40036`
- 移动：先更新场景坐标，再 `Response`，然后把 `onMove` 和进出视野交给进程内广播队列
- 聊天：禁言检查仍在回包前做。先入广播队列，成功才 `Response`，再推 `onChat`
- 移动按发送者合并：同一人还有没推完的旧坐标时，只留最新坐标。进出视野在真正推送时，用「上次已经广播的位置」和「当前坐标」现算
- 聊天不合并

### 不包含

- 修改 `cherry-framework`
- 降低 bcrypt 成本，或把哈希改成异步回调后再补发 token
- 网关替客户端自动重试 `40036`
- 改 20 秒的 `request_timeout`
- 改 AOI 半径、分线人数、战斗结算
- 装备穿脱、强化、暴击这三项的压测

## 协议设计

| 类型 | Route / 事件 | 请求 | 响应 / Push | 说明 |
|------|----------------|------|-------------|------|
| RPC | `gate.user.issueToken` | 不变 | 不变，或码 `40036` | 密码工人满时马上拒绝 |
| RPC | `gate.user.refreshToken` / `login` / `logout` | 不变 | 不变 | 只打 session 工人 |
| RPC | `game.player.move` | 不变 | 空包 | 坐标已写入才回包。推送落后不改变这个成功 |
| Push | `onMove` | — | 不变 | 可以少中间档，不能把人留在旧坐标上不更新 |
| RPC | `game.chat.send` | 不变 | 空包，或码 `40037` | 入队失败不回成功 |
| Push | `onChat` | — | 不变 | 不合并、不丢已入队的一条 |

**业务错误码：**

- `40036` `LoginBusy`：签发时密码工人排队已满
- `40037` `ChatBusy`：聊天广播队列已满
- `40005` 仍只表示没有登录节点，或 RPC 本身失败。排队满了不再用它

**前置条件：** 移动和聊天仍须已进场。签发的参数、设备号、密码错误、限流、封禁、维护码都不变。

客户端遇到 `40036` 自己退避再试。服务端不重试。

## 数据与持久化

| 表 / 缓存 | 字段 / Key | 索引 / TTL | 说明 |
|-----------|------------|------------|------|
| 无新表 | — | — | 账号、token、场景坐标的存法不变 |

**事务：** 签发仍走现有的建号和写 token。哈希仍在密码工人这条调用里同步完成，只是不再占用 session 工人的邮箱。广播队列只在内存，不落库。

MySQL `max_open_conns` 必须大于「密码工人 + session 工人」。按上面的公式，现有 20 够用，这次不改连接池。

## 业务规则

- 密码工人一次只处理一条签发。Actor 的邮箱就是队列，上限 32，含正在算的那一条。轮询到已满的工人就换下一个；都满才返回 `40036`
- `bcrypt` 成本保持默认。校验旧密码和生成新密码都算在密码工人里
- 移动的坐标在回包前写入 `world`。广播队列按发送者只留最新一档。推送时再算进出视野，避免合并后把已经走过的中间圈漏掉或重复
- 广播队列长度 4096，移动和聊天共用这一个进程内队列，聊天任务不参与按人合并。队列满时，移动仍回成功并丢掉这一档还没进队的广播；聊天回 `40037`
- 战斗心跳里已有的快照推送不改。这次只把玩家移动请求路径上的 `PublishMove` 放进同一个队列，并且跟该次 `onMove` 一起在推送时计算

## 验收标准

- [ ] 密码工人全满时，新的签发返回 `40036`，不等到 20 秒，也不返回 `40005`
- [ ] 密码错误仍是 `40010`，失败过多仍是 `40014`，封禁 `40033`，维护 `40035`
- [ ] 签发正在排队时，刷新不进入密码工人
- [ ] 移动回包时坐标已经是新的。同一人连续两次移动，周围的人至少能看到后一次坐标
- [ ] 聊天队列有空位时回成功并最终收到 `onChat`。队列满时回 `40037`，发送方不收到一条假装成功的空回包
- [ ] `go test` 覆盖密码工人满员、移动先回包、聊天队列满
- [ ] 不改 cherry。不降低 bcrypt 成本

## 风险与依赖

| 项 | 说明 |
|----|------|
| 依赖 | 现有登录轮询、`world.BroadcastMove` / `BroadcastChat`、战斗进出视野 |
| 迁移 | 无表结构变更。旧客户端把 `40036` 显示成登录失败即可，不需要新字段 |
| 兼容 | 移动广播改为可能跳过中间坐标。聊天从「先推完再回包」变成「入队成功才回包」 |
| 容量 | 这一期不保证 2000 人同时签发全部成功。哈希吞吐仍受 CPU 限制，多出来的是 `40036` |
| 压测 | 代码落地后再改 `docs/plans/load-test.md`。提交前压测结果保持进行中 |
