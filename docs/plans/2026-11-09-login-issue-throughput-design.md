## 背景与目标

2026-11-09 重跑 LT-01（2000 人同时 `gate.user.issueToken`）：成功 384，`40036` 1616，`40005` 已归零，墙钟 6.26 秒。`40036` 把「排队到超时」换成了「快速拒绝」，这一层已经达标。但服务端在 20 秒窗口内只能吃下约 380 个新建号，超出部分靠客户端退避重试。

**一期目标：** 让服务端在 20 秒 `request_timeout` 窗口内自己吃下 2000 个全新建号，不需要客户端重试。做法是把 bcrypt 哈希移出数据库事务，并按连接池重新配工人数与连接上限。

---

## 用户场景

1. 开服 / 活动开场，2000 个新账号在同一时刻点登录。全部拿到 token，没有 `40036`，没有 `40005`。
2. 2000 个**已有账号**同时登录。走 Redis 缓存命中，只做一次 bcrypt 校验，比新建号更快。
3. 超出容量（例如 4000 人）的尖峰。服务端仍然快速返回 `40036`，客户端退避重试后成功；不出现 `40005` 或 20 秒挂起。

## 实测数据

| 项 | 值 | 来源 |
|----|----|------|
| bcrypt cost 10 单次 | 57 ms | 本机 i5-10400F，`benchtime 20x` |
| 2000 个新号纯哈希 | 114 核·秒 | 2000 × 57ms |
| Docker VM 核数 | 12 | `docker info` |
| 当前每节点密码工人 | 6 | `min(12/2, 20−8−4)` |
| 当前总并发容量 | 384 | 2 节点 × 6 工人 × 32 名额 |
| 当前实际单请求耗时 | 196 ms | 6.26s / 384 有效并发，反推 |
| 当前吞吐 | 约 61 个/秒 | 384 / 6.26s |
| 2000 个所需时间 | 32.6 秒 | 2000 / 61 |

哈希 57ms，但实测单请求 196ms。差的约 139ms 是数据库事务往返。原因是 `hashPassword` 在 `WithinTx` 内部执行（`internal/persistence/account.go:126`），哈希这 57ms 全程占着一条 MySQL 连接和事务。

---

## 功能范围

### 包含

- 把密码哈希移出数据库事务：先算哈希，再开事务写库
- `mysql.max_open_conns` 由 20 提到 40（profile 配置，不改代码常量）
- `PasswordWorkersFrom` 的连接池预留公式随之调整，让工人数能随连接池增长
- 文档补 `40036` 的客户端处理约定（退避重试）

### 不包含

- 降低 bcrypt cost（安全基线不动）
- 客户端自动重试的实现（本次只定义约定，客户端各自实现）
- 把哈希改成异步回调后再补发 token（会改变语义）
- 改 20 秒的 `cluster.nats.request_timeout`
- 改 Redis 账号缓存的 TTL 与结构
- 无上限排队缓冲

## 协议设计

| 类型 | Route / 事件 | 请求 | 响应 / Push | 说明 |
|------|----------------|------|-------------|------|
| RPC | `gate.user.issueToken` | 不变 | 不变 | 本次不改协议 |
| RPC | `gate.user.refreshToken` / `login` / `logout` | 不变 | 不变 | 同上 |

**业务错误码草案：** 不新增。`40036` `LoginBusy` 语义不变，仍表示「密码工人排队已满，请退避后重试」。

**前置条件：** 无变化。

**客户端约定（本文档定义，本次不改代码）：** 收到 `40036` 后按 200ms 起、指数退避、上限 2 秒重试，总重试预算建议 30 秒。不得把 `40036` 展示成「登录失败」。

## 数据与持久化

| 表 / 缓存 | 字段 / Key | 索引 / TTL | 说明 |
|-----------|------------|------------|------|
| `accounts` | 不变 | 不变 | 仅调整写入时机，表结构不动 |
| Redis 账号缓存 | `{prefix}:account:nickname:{nickname}` | `cache_ttl_seconds` | 不变 |

**事务：** `LoginOrCreateAccountContext` 的改造点：

1. 先查 Redis 缓存（现状已如此，事务之外），命中则校验密码后直接返回
2. 未命中时，**先在事务外**计算 `bcrypt` 哈希（仅新建路径需要）
3. 再开 `WithinTx`，在事务内完成「查账号 → 命中则校验 → 未命中则用已算好的哈希插入」
4. `AfterCommit` 刷缓存的行为保持

这样连接持有时间从约 196ms 降到约 139ms，并且在等哈希时不占连接。

---

## 业务规则

- 哈希移出事务后，「查账号 → 插入」之间仍必须在事务内完成，避免并发建出重复账号
- 事务内再次查到账号（说明被别的请求抢先建了），要用 `verifyPassword` 校验后复用，沿用现有逻辑
- 事务外算的哈希在「账号已存在」分支被丢弃，属于可接受的浪费；不得为此回填使用
- 工人数上限仍受连接池约束：`room = openConns − sessionWorkers − 4`，公式不变，只是 `openConns` 变大
- 连接池上限必须大于「密码工人 + session 工人」，否则工人拿不到连接会退化为排队

**容量核算（改造后）：**

| 项 | 值 |
|----|----|
| `max_open_conns` | 40 |
| 每节点密码工人 | `min(12/2, 40−8−4)` = 6 → 实际仍受核数限制 |
| 每节点 session 工人 | 8 |
| 总并发 | 2 × 6 = 12 → 需按下面确认 |

**已定（评审结论）：** 工人数改为按可用连接数优先，不再受核数平分限制。每节点 16 工人、总并发 32，吞吐约 230 个/秒，2000 个约 8.7 秒。哈希移出事务与连接池提到 40 一并执行。

`room = openConns − sessionWorkers − 4` 在当前配置下为 `40 − 8 − 4 = 28`，取核数平分与 room 的较小值仍是 6，所以**必须显式改公式**：改为 `min(max(2, openConns − sessionWorkers − 4), 16)`，即连接池允许多少就用多少，但不超过 16 的上限（`SessionWorkers` 已有同样的 16 上限，保持一致）。

## 风险与依赖

| 项 | 说明 |
|----|------|
| 依赖 | 无。改动集中在 `internal/persistence`、`internal/authcfg` 与 profile |
| 迁移 | 无表结构变更 |
| 兼容 | 协议不变，老客户端无感。仅新增「`40036` 应退避重试」的约定 |
| 容量 | 放宽核数约束会占用更多 CPU，需在 12 核上实测哈希期间 game/gateway 的延迟是否受影响 |
| 安全 | bcrypt cost 保持默认，不降级 |
| 不确定性 | 「并发 14 是否真的等于吞吐 2000/20s」按线性外推得到，实测可能有超线性或次线性偏差，以压测为准 |
