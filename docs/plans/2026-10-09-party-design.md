# 组队 策划文档

> **Status:** approved  
> **实施计划：** （策划通过后创建）[`2026-10-09-party.md`](2026-10-09-party.md)

**For agentic workers:** 本期做正式组队，并且允许不同游戏节点上的玩家进同一支队伍。名单放在 Redis。邀请和名单变化经 NATS 通知对方所在的游戏节点，再由那个节点推给网关。不发奖励，不要求同图同线。不做客户端。

---

## 背景与目标

现在没有队伍。世界 BOSS 需要「同一支队伍里至少两人出力」才能发组队奖，但邀请、队长和离队不能写进击杀结算里。

**一期目标：** 已进场的玩家可以组建最多 4 人的队伍，队员可以分别在不同的游戏节点（例如 `10001` 和 `10002`）。队长邀请，对方 30 秒内接受或拒绝。断线后席位保留 60 秒，期间重新进场回到原位；超时再离队。切图不离队。一人同时只在一支队伍。

---

## 用户场景

1. 玩家已进场，创建队伍，自己成为队长。邀请另一名已进场的玩家。对方收到邀请，30 秒内接受，加入队尾。双方都收到成员名单。
2. 对方拒绝，或 30 秒没有回应。队伍成员不变，这条邀请作废。
3. 队长踢出一名队员。被踢的人收到空名单，其余人收到新名单。队长自己离队时，最早加入的队员成为队长。队里只剩队长一人时再离队，队伍解散。
4. 队员断线后，席位还留 60 秒，仍然占着 4 人上限。他在这 60 秒内重新进场，自动回到原来的加入顺序，不必再被邀请。超过 60 秒还没回来，按离队处理；离线的是队长，则最早加入的队员接任。队员切到另一张图或另一条线，仍留在队里，不开始这 60 秒。队长在 `10001`，队员在 `10002`，两边看到的是同一份名单。

---

## 功能范围

### 包含

- `game.party.create`、`invite`、`answer`、`leave`、`kick`、`state`
- 推送 `onParty`、`onPartyInvite`
- 队伍上限 4 人，一人同时只在一支队伍
- 邀请 30 秒有效；同一目标只保留最新一条邀请
- 断线后席位保留 60 秒，时限内重新进场回到原位；超时再离队。切图、换线不离队，也不开始这 60 秒
- 不同游戏节点之间可以邀请、接受、离队和踢人
- 错误码 `40060`–`40065`

### 不包含

- 击杀奖励、伤害统计、同图同线限制
- 跟随、队伍聊天、经验分享、就绪确认
- 离线邀请、邮件
- 跨服传送、跨服进同一张世界 BOSS 线
- 客户端
- 单独再做一个组队进程。断线宽限靠 Redis 里的到期时间，不靠本机定时器

## 协议设计

这些路由不放进网关的进场前白名单。未进场仍返回 `40009`。

| 类型 | Route / 事件 | 请求 | 响应 / Push | 说明 |
|------|----------------|------|-------------|------|
| RPC | `game.party.create` | `Empty` | `PartyState` | 创建并成为队长 |
| RPC | `game.party.invite` | `PartyInviteRequest` | `Empty` | 队长填写目标 uid |
| RPC | `game.party.answer` | `PartyAnswerRequest` | `PartyState` | 接受时返回新名单；拒绝时返回空名单 |
| RPC | `game.party.leave` | `Empty` | `Empty` | 自己离队 |
| RPC | `game.party.kick` | `PartyKickRequest` | `Empty` | 队长填写队员 uid |
| RPC | `game.party.state` | `Empty` | `PartyState` | 查询自己当前名单 |
| Push | `onParty` | — | `PartyState` | 成员或队长变化时，推给仍在队内的人；离队者收到空名单 |
| Push | `onPartyInvite` | — | `PartyInvite` | 只推给被邀请者 |

`PartyInviteRequest` 只有目标 uid。`PartyAnswerRequest` 带邀请 id 和是否接受。`PartyKickRequest` 带队员 uid。

`PartyState` 带队伍 id、队长 uid、按加入顺序排列的成员 uid。没有队伍时队伍 id 为 0，成员为空。`PartyInvite` 带邀请 id、队伍 id、队长 uid、到期的毫秒时间。邀请被覆盖、拒绝或过期时，再推一条邀请 id 为 0 的 `PartyInvite` 给原目标。

**业务错误码草案：**

| 码 | 常量 | 说明 |
|----|------|------|
| 40060 | `PartyAlreadyIn` | 自己已经在队伍中，或邀请目标已经在队伍中 |
| 40061 | `PartyNotIn` | 自己不在队伍中 |
| 40062 | `PartyNotLeader` | 不是队长，不能邀请或踢人 |
| 40063 | `PartyInviteInvalid` | 邀请不存在、已处理、已超过 30 秒，或目标不是本队队员 |
| 40064 | `PartyFull` | 接受时队伍已经有 4 人 |
| 40065 | `PartyTargetOffline` | 邀请目标未进场 |

未进场仍是 `40009`。

**前置条件：** 调用方已进场。邀请目标也必须已进场。

## 数据与持久化

| 表 / 缓存 | 字段 / Key | 索引 / TTL | 说明 |
|-----------|------------|------------|------|
| Redis | `party:{partyId}`：队长 uid、按加入顺序的成员 uid | 解散即删 | 队伍 id 用创建者所在游戏节点的雪花 `NextID()` |
| Redis | `party:uid:{uid}` → partyId | 离队即删 | 判断某人现在哪支队伍 |
| Redis | `party:invite:{uid}`：邀请 id、partyId、队长 uid、到期毫秒 | 30 秒 | 同一目标只保留一条 |
| Redis | `party:online:{uid}` → 游戏节点 id | 离场即删 | 进场时写下，用来找到对方在哪个节点。断线时删掉，宽限期内不写 |
| Redis | 成员上的 `graceUntil` 毫秒 | 宽限 60 秒 | 断线时写成现在加 60 秒。重新进场或宽限作废时清掉。切图不写 |
| 本机内存 | 已进场玩家的网关路径 | 离场即删 | 只给本节点上的人推 `onParty` |

**事务：** 不写 MySQL。同一支队伍的加入、离队、踢人，对 `party:{partyId}` 做一次原子更新。邀请用 `party:invite:{uid}` 覆盖写。

**热更：** 没有配表。

节点之间不共享内存。名单变了以后，按 `party:online:{uid}` 找到每个成员所在的游戏节点，用现有 NATS 集群调用那个节点上的投递方法。那个节点只负责推给自己进场表里的人。节点没投递成功时，名单仍然以 Redis 为准，成员下次 `game.party.state` 能读到。

## 业务规则

- 队伍按账号 uid 记。不按角色 id。一人同时只在一支队伍。
- 创建时自己就是队长，也是加入顺序的第一人。已经在队里再创建，返回 `40060`。
- 只有队长可以邀请和踢人。队员做这两件事返回 `40062`。
- 不能邀请自己，返回 `40063`。目标已经在任意队伍里，包括还在 60 秒宽限内，返回 `40060`。目标不在任何队伍，且 `party:online:{uid}` 没有他，返回 `40065`。目标在别的游戏节点上，一样可以邀请。宽限内的人没有在线节点，但因为还占着队伍名额，走 `40060`，不走 `40065`。
- 邀请发出时不占人数。接受时队伍已满返回 `40064`，邀请作废。
- 同一目标已有待处理邀请时，新邀请覆盖旧的。旧邀请 id 立刻失效，并给目标推一条空邀请。
- 邀请从发出时起 30 秒内有效。超时后的接受或拒绝返回 `40063`。
- 接受时人必须仍在场，且仍不在任何队伍里。成功后加到成员末尾。拒绝只作废邀请，不改变队伍。
- 有人离队时，先把他从名单去掉。剩下不少于 2 人，并且离队的是队长：队长交给剩下的人里最早加入的那一位。剩下 0 人或 1 人：队伍解散，留下的那个人也变为无队伍。
- 队长不能踢自己，改走离队。踢人目标不是本队成员，返回 `40063`。宽限内的队员仍是本队成员，可以被踢，踢掉后宽限作废。
- 玩家离开当前游戏节点（断线、回选角、被踢下线）时不立刻离队。删掉 `party:online:{uid}`，把该成员的 `graceUntil` 写成现在加 60 秒。这 60 秒里他仍占名额，仍留在原来的加入顺序上。切图和换线不离队，不写 `graceUntil`，也不改在线节点。
- 宽限内重新进场：人还在名单里，且 `graceUntil` 未到或还没有这个标记。清掉 `graceUntil`，写下新的 `party:online:{uid}`，位置不变。没有 `graceUntil` 表示进程中断后来了，同样回到原位。
- 宽限已过再进场，或任何队伍操作发现某成员的 `graceUntil` 已过：按离队处理。离队的是队长时，队长交给剩下的人里最早加入的那一位。剩下不足 2 人则队伍解散。过期之后不会自动加回队尾。
- 队伍不检查成员是否在同一张图、同一条线、同一个游戏节点。世界 BOSS 发奖时再读 Redis 里的名单，并且仍然要求人在死怪的那张图、那条线。跨服队友不在这条线上，就没有这次击杀的份。位置规则见 [`2026-10-09-world-boss-design.md`](2026-10-09-world-boss-design.md)。
- 成员变化后，仍在队内的人各收到一份相同的 `onParty`。刚离开的人收到空 `PartyState`。开始 60 秒宽限时名单没变，不推空名单。宽限到期并离队时，才按离队推送。

## 验收标准

- [ ] 已进场玩家可以创建队伍并成为队长；未进场返回 `40009`；已在队里再创建返回 `40060`
- [ ] 队长邀请已进场玩家，对方 30 秒内接受后出现在队尾；拒绝或超时后成员不变
- [ ] 邀请自己、邀请未进场、非队长邀请，分别返回 `40063`、`40065`、`40062`
- [ ] 目标已在队伍中返回 `40060`；接受时队满返回 `40064`
- [ ] 新邀请覆盖旧邀请，旧邀请 id 不能再接受
- [ ] 队长离队后，最早加入的队员成为队长；只剩 1 人时离队则队伍解散
- [ ] 队长踢人后，被踢者收到空名单；队长踢自己返回 `40063`
- [ ] 断线后 60 秒内重新进场，仍在原队伍的原位置，且这 60 秒仍占 4 人上限；超过 60 秒再进场则已离队。切图后 `state` 仍能看到原队伍
- [ ] `10001` 上的队长邀请 `10002` 上已进场的玩家，对方接受后两边 `state` 是同一份名单；`10002` 断线超过 60 秒后两边都不再包含他
- [ ] `go test ./...` 通过

## 风险与依赖

| 项 | 说明 |
|----|------|
| 依赖 | 已进场才能拿到网关路径。离场回调只写 60 秒宽限，不立刻离队。节点之间用现有 NATS 集群调用 |
| 迁移 | 无 MySQL 新表。Redis 增加 `party:*` 键，无旧数据要迁 |
| 兼容 | 新路由。旧客户端不调用则没有队伍。客户端协议不带游戏节点 id |
| 跨服 | 只打通队伍名单和推送。不把两个节点的场景、怪物或背包合成一份 |
| 残留 | 断线宽限写在 Redis 的 `graceUntil` 上，不靠本机定时器。进程崩溃没写上宽限时，该玩家下次进场仍回到原位。一直不回来的人要等下一次队伍操作发现过期；崩溃且没写宽限的，不会自动过期 |
| 后续 | 世界 BOSS 读 Redis 名单，不在本期发奖 |
